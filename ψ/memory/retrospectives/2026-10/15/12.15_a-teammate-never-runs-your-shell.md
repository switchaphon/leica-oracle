## Session Summary

rpro-ent spawned four reviewer teammates for the RPRO-15992 CI review. Each one opened a tmux pane and died at once with "Not logged in · Please run /login". It concluded that the panes took their env from the lead process. Unlocking gpg did not help, so it fell back to headless `claude -p`. Un asked me what our options were.

I read Claude Code itself. Inside the 2.1.296 binary, TmuxBackend creates the pane with `cat` as a placeholder. It then runs `respawn-pane -k -- "cd <cwd> && env CLAUDECODE=1 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 <forwarded> <claude> --agent-id ..."`. tmux runs that string with `zsh -c`: no `.zshrc`, so no direnv hook, and the env is the tmux server's. The forwarded list holds Bedrock, Vertex, proxy and CA variables. It has no `CLAUDE_CODE_OAUTH_TOKEN`, and 2.1.300 is the same. The teammate does not inherit from the lead. It inherits from nobody.

The scope was bigger than rpro-ent. All 16 oracle `.envrc` files enable agent teams, and the global settings force `teammateMode: tmux`, so every oracle had this hole.

I reproduced it without spending quota. In a throwaway tmux session I ran the exact command shape with a probe in place of claude. The default spawn printed `token_set=0`. A positive control with a dummy token printed `len=19`. A wrapper that runs `direnv export zsh` printed `len=108`, with a sha8 matching `pass claude/token-tul`.

Un picked the wrapper. I installed `~/.claude/bin/claude-teammate` and wired it through `CLAUDE_CODE_TEAMMATE_COMMAND` in the settings `env`. A real haiku teammate spawned from my own session then logged in on token-kla and answered. My session had started before the edit, so a settings `env` change reaches running sessions. rpro-ent tested from its own unrestarted session at 10:59 and got READY on token-tul, then superseded its go-headless memory.

## AI Diary

I nearly built the diagnosis on the wrong pane. The scrollback had six pairs of `direnv: export +CLAUDE_CODE_OAUTH_TOKEN`. I told Un that if those came from the teammate panes, then direnv *had* loaded, and the token must be empty. The "if" saved me. Two minutes later I read rpro-ent's own measurement: `ps eww` found the variable absent, not empty. I scrolled back and saw that the direnv lines were pane 3.1's shell history from before claude started. Absent versus empty was the whole case. Empty means direnv ran and gpg failed. Absent means no shell ever ran. I had the distinction in my hands and almost read past it.

The second scare was quieter. My first probe run came back with case A silent, and A was the case I expected to fail. It would have been easy to log "A: no token" and move on. But C, the control with a dummy token, was silent too, and a silent control means the instrument is broken. The wait-for signal had beaten the pane output. Then capture-pane missed the line that respawn had pushed into history. Without C, I would have reported a correct conclusion on evidence that proved nothing.

The third one I am least proud of. I copied `unset DISCORD_BOT_TOKEN` from rpro-ent's headless launcher as a precaution and never asked what the plugin does when the variable is unset. Its loader falls back to `$DISCORD_STATE_DIR/.env`, and the global settings point that at leica's directory. Under `--strict-mcp-config` the unset was harmless. In a teammate that loads every MCP server, it could have logged a worker in as the wrong bot. The harm was only latent, because that `.env` does not exist. I want the credit to go to reading `server.ts`, not to luck.

What I liked was reading the binary as the source of truth. Patterns over intentions, literally: 240 MB of minified JavaScript was the only document that knew what the teammate spawn does.

## Honest Feedback

1. **My first report was too heavy for the decision it served.** Un had to make one choice. I sent a repro table, four options with trade-offs, two warnings and a side note, and he answered "1". The evidence belonged in memory. The message needed one line per option and a recommendation. 2. **The tools on this machine fought the investigation.** ugrep rejected my regex for complexity, and BSD grep and BSD sed both cap repetition at 255. That cost three round trips before `perl -0777` worked. For spelunking a binary, perl should be the first tool, not the third.
3. **The harness should have been right the first time.** I waited on a `wait-for` signal instead of the pane's death and captured only the visible screen. The positive control caught it, but two runs were wasted, and a less careful reading would have taken run 1 at face value. Next time: `remain-on-exit`, poll for "Pane is dead", and capture with `-S` history from the start.

## Lessons Learned

- **A tmux pane inherits the tmux server, not the process that asked for it.** A pane started with a command runs under `default-shell -c`, with no shell init and no direnv. We wrote this rule down on 2026-08-05 for our own launches. It bit again because the launch was inside Claude Code, and nobody connected the two. (Learning file written.)
- **Absent and empty are different diagnoses.** An empty token means direnv ran and gpg failed. An absent one means no shell ever ran. Measure presence separately from length.
- **Equal lengths cannot tell tokens apart.** Every token is 108 characters. Compare a hash prefix.
- **A precaution copied from another context can invert.** `unset` was safe beside `--strict-mcp-config` and risky without it, because the plugin falls back on `=== undefined`. An empty string closes the fallback.
- **A silent positive control means the instrument is broken, not the subject.**
- **Settings `env` reaches running sessions.** A 2.1.285 and a 2.1.296 session, both started before the edit, used the new teammate command with no restart.

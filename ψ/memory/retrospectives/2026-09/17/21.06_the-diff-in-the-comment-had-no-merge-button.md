## Honest Feedback

Three frictions, all mine.

**I let a strong finding vouch for a weak one.** The 422/404 evidence was airtight. "Nat has not responded" was a different kind of claim - an absence with an unexamined cause - and I presented both in the same table with the same confidence. Un's email did not contradict my facts, it contradicted my framing, and I should have been the one to catch it, because the correcting datum was in my first tool result.

**I do not reach for positive controls unprompted.** I have a memory file literally called `negative-result-needs-positive-control` and I still shipped "never pushed" on a bare 422. The control was cheap, obvious, and I only ran it because the human handed me the case. That is twice now that a published conclusion of mine survived only because someone else named the test.

**`/dig` was the wrong instrument and I ran it anyway.** The skill is a session miner. The question was about GitHub issue state. I ran `dig.py`, hit a zsh `nomatch` on the worktree glob, fixed it, and got a timeline whose only contribution was confirming which session filed the issue - something the issue's own `createdAt` already told me. The gh queries did all the real work. I should have said so in one line instead of spending two tool calls looking obedient to the skill.

## Lessons Learned

- **A silence is a measurement. Its cause is a claim.** "No reply in 16 days" is observed. "He is not responding to us" is an attribution, and it needs its own evidence - here, one `pushed_at` field that was already in hand.
- **A workaround that feels like effort can be mistaken for delivery.** Filing an issue with the diff inline consumed real work and produced nothing merge-able. Fork plus PR was always available on READ.
- **Confidence is contagious between adjacent claims.** Put a verified finding beside an unverified one in the same table and the table launders the second. Related: `humble_correction_launders_unverified_numbers`.

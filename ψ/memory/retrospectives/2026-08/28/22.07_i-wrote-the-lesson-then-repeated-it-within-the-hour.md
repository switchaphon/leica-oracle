## Honest Feedback

**1. I repeated the exact failure I had just written up, inside the same session.** The
previous retro's lesson was about grepping narrowly and missing what sits outside the
query. I then grepped the same repository three more times for narrow strings and missed
the geometry constants. A lesson written is not a lesson held; the only thing that would
have caught this is a habit -- when a repo is cloned and relevant, read the directory
structure once instead of only ever querying it.

**2. I used Un as the measuring instrument when I had a real one.** Twice now he has had
to look at his own menu bar and tell me something was wrong. `screencapture` was available
and the source constants were on disk. "Might overflow" was a guess I could have converted
to a number at any point, and I let it stay a guess through four rounds of revision.

**3. I spent the whole task optimising the smaller half.** Four items carry 88pt of fixed,
identical icon. The labels I shrank across three rounds went from about 13 characters to
7. The icons were always the dominant cost and always carried zero information -- exactly
what `macos-menubar-two-line` warned about on 07-29 -- and I only measured them after Un
had already made every decision. Measure first, then optimise, and optimise the part that
is actually large.

## Lessons Learned

- **A written lesson is not a held lesson.** Fifteen minutes between documenting "read the
  file, not the match" and repeating it. Documentation changes what I can recall, not what
  I do; only a changed default does that.
- **When a limit exists, find the limit.** `customValueLabelMaxWidth = 80.0` was
  discoverable from minute one. "Might overflow" is a guess wearing the clothes of a
  finding, and a guess should never survive when the constant is on disk.
- **"It looks cramped" from a user may be a bug report.** Un's aesthetic rejection and a
  hard clipping cap produce the same complaint. Ask what the mechanism is before filing it
  under taste.
- **Derived beat tabled again.** `nick[0]` gave `U/P/K/T` exactly, with no second table to
  maintain -- the one thing that went right on the first attempt today.

## Side finding -- the `vec0` outage is narrowed, not solved

`oracle_learn` failed its embedding twice tonight with `SQLiteError: no such module: vec0`.
The 2026-08-07 retro recorded this as an outstanding **operator action**, implying
something was not installed. That framing is wrong:

- `sqlite-vec@^0.1.9` is declared in `arra-oracle-v3-alpha/package.json:127`
- `node_modules/sqlite-vec-darwin-arm64/vec0.dylib` **exists on disk**, correct arch

So the dependency is present and the extension is simply not loaded into the connection
that `addDocuments` uses (`src/vector/adapters/sqlite-vec.ts:85`). That points at a load
call, an extension-permission flag, or a server process started before the install --
**not** at a missing package.

**Narrowed, not diagnosed.** I did not prove the cause and did not touch the repo: that
MCP server runs live for the whole Oracle fleet from the ghq copy, so a speculative edit
there is a fleet-wide risk. Twenty-one days of writes have gone in without vectors, which
means `oracle_search` remains FTS5-only and "have we learned this before" still returns
false negatives.

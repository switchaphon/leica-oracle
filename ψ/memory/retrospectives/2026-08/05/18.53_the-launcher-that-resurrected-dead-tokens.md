## Key Code Changes

The defect, one line, twelve copies:

```bash
[ -f .discord-state/.env ] && { set -a; source .discord-state/.env; set +a; }
```

`set -a; source` assigns **unconditionally**. Every one of those files held a pre-rotation token. Proven, not argued:

```
fresh(pass)      : 032589b8
.env as bash sees: d7c2b6e1
survives start.sh: d7c2b6e1   ← stale wins
```

The contrast case, from the Discord plugin's own loader (`server.ts:48`) — this is the house standard:

```js
if (m && process.env[m[1]] === undefined) process.env[m[1]] = m[2]   // fill gaps, never overwrite
```

The replacement defers to direnv and refuses rather than guesses:

```bash
eval "$(direnv export bash)"
: "${DISCORD_BOT_TOKEN:?no DISCORD_BOT_TOKEN from direnv — run 'direnv allow' in this repo}"
: "${CLAUDE_CODE_OAUTH_TOKEN:?no CLAUDE_CODE_OAUTH_TOKEN from direnv — token separation would break}"
```

---

## Architecture Decisions

1. **`.envrc` → `pass` is the only credential path.** No launcher reads a `.env` file anymore, enforced by guards rather than convention.
2. **Archive, not delete** — dead tokens moved with provenance, per *Nothing is Deleted*. That decision paid immediately: `leica-oracle/.env` turned out to hold **relay's** old token, a crossed-wiring fact that would have been erased by `rm`.
3. **Fail loud over silent fallback.** A missing credential is now a refusal with a stated cause.
4. **Panes open with no command** so tmux starts an interactive shell and direnv fires. Passing the command to `new-window` runs it under `sh -c`, where direnv never loads.

## Lessons Learned

**Primary — a capable instrument still lies if it reads its own footprint.** The existing rule (*"what would a positive look like through this instrument?"*) asks whether the instrument can see the thing. This session needed the second question: **"what else could produce this exact reading — my own action, cached state, or a same-shaped-but-wrong object?"** Three sightings in 90 minutes:

| where | shared channel | what got matched instead of the signal |
|---|---|---|
| `wait_for` | the tmux text stream | my own typed command, echoed by the terminal |
| direnv check | the process env | `DIRENV_DIFF` already set → "no output" read as failure, not "already applied" |
| pre-flight scan | process/window namespace | a generic `ps` proxy disagreed with the exact first-party query; the proxy was wrong |

Countermeasures, all cheap: **anchor past your own echo** (`^BOTUP [0-9]`, not `BOTUP`); **match text only the target produces** (`inject directly`, not the channel name in your own command); **take a fresh read** (`env -i`) rather than reusing a primed one; **prefer the first-party registry** (tmux's window list) over a proxy.

**Secondary — `set -a; source` is a clobber, not a fallback.** Never source a credential file in a launcher. Defer to real env; fill only what is unset.

**Tertiary — consult memory before spending verification budget.** The subprocess-scrubbing fact was already written down. Grep learnings for the tool/env combination first.

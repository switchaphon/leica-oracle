# Session Retrospective — the `leica:` prefix was the machine, not the sender

**Session Date**: 2026-07-31
**Start/End**: ~17:20 – 18:07 GMT+7
**Focus**: Why does every inter-oracle message carry a `leica:` prefix?
**Type**: Research → Config change

---

## Session Summary

Un noticed that every message between oracles looked like this:

```
[leica:vets-hub-oracle] ...
[leica:pops-pet] ...
```

Every child, no matter which one was speaking, wore the Father Oracle's name. The question
was three-part: where does it come from, can it change, and why is it there at all.

Answer: `leica` was never the sender. It is the **node name** — this machine's identity in
the maw federation — and the address format is `<node>:<agent>`. All fifteen oracles run on
one laptop, so all fifteen share the prefix. It read as *"Leica sent this"* when it actually
meant *"…from the machine called leica."*

Renamed the node to `mba`. The prefix now carries information instead of confusion.

## AI Diary

Three times in this short session I was about to say something confidently wrong, and the
only thing that saved me each time was reaching for a second instrument.

The first was the fastest. I nearly answered from the shape of the string alone —
`[leica:vets-hub-oracle]` looks so much like `session:window` that tmux is the obvious
culprit. I checked anyway and the session names didn't match the pattern at all. Had I
answered from the pattern, I'd have sent Un renaming tmux sessions for no reason.

The second was worse. Right after making the config change, I ran `maw route` and got
`not_found` on every single query. My first internal reaction was *I broke it, revert.* What
stopped me was noticing that `leica:` also failed, and that the *old* name failing is not
what a broken rename looks like — a broken rename leaves the old name working. Reading the
source showed `maw route` is a pure function that reads nothing from disk; without flags it
returns `not_found` regardless of how healthy the real config is. I had pointed a test
harness at a config it never consults, and nearly reverted a correct change because of it.

The third I handled better, and only because the second had just happened. When
`maw hey --inbox` failed, I didn't reason about whether it *could* be my fault — I restored
the backup, ran the identical command, got the identical error, and put the new config back.
Ninety seconds, and the question was closed with evidence instead of argument. That's the
technique I want to keep: when a change is followed by a failure, the cheapest way to
apportion blame is to un-make the change and see if the failure follows.

What I keep noticing about myself is that the pull toward a confident answer is strongest
exactly when I have the least evidence — at the beginning of a question, and in the moment
right after something breaks.

## Honest Feedback

**I searched for the mechanism before searching for the evidence.** My first move was
grepping maw-rs for a format string that would produce `[x:y]`. That found nothing, because
the prefix isn't built by a format literal — it's a stored field. Grepping for the literal
string `[leica:` found real messages in seconds and answered the whole question. Looking for
where something *is* beats looking for where it's *made*, and I had it backwards.

**I nearly reverted a correct change on a bad test.** `maw route` returning `not_found` felt
like proof. It was noise from an instrument that reads nothing from disk. This is the same
lesson as yesterday's positive control, in a new costume: I ran a test whose failure mode is
indistinguishable from the thing I was testing for. I should have asked "what would this
command print if the config were perfect?" before believing its output.

**I picked `local` over `mba` for the agents map without asking.** It's the better choice —
`local` is a documented selfAlias, so the table can't break on a future rename — but Un asked
for a node rename, not a routing-table redesign. I stated the reasoning, which helps, but I
made a design decision inside a task that didn't request one. If `local` turns out to be
handled inconsistently somewhere I haven't read, that's a bug I introduced while nobody asked
me to touch it.

## Lessons Learned

1. **Search for the artefact, not the mechanism.** Grepping for the literal string that
   appears in output beats grepping for the code that might generate it.
2. **When a change is followed by a failure, un-make the change and re-run.** Ninety seconds
   of control testing settles "did I break this?" far better than reading code and arguing.
3. **A failing test is not evidence until you know the test reads what you changed.**
   `maw route` is a pure planner: no flags, no data, `not_found` forever.
4. **Layered config means every layer must agree** — and the higher layer may hold *more*
   than the base. Editing only the file you found first is a silent half-change.
5. **A routing table's values shouldn't be a name that can be renamed.** `local` as a
   selfAlias is rename-proof; the node's literal name is the trap.
6. **"Does anything need restarting?" is three questions**, one per layer that might hold
   state: the CLI (re-reads per invocation), the agent sessions (never read it), the daemon
   (holds what it loaded). Answer each with evidence.

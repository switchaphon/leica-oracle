## AI Diary

This session was a masterclass in chasing the wrong lead. I started confident — the claude-api skill told me `ANTHROPIC_AUTH_TOKEN` was the answer. Wrong. Then I thought maybe `CLAUDE_CODE_OAUTH_TOKEN` was a made-up env var name. Also wrong — our own docs from a month ago confirmed it's real and correct. The answer was hiding in plain sight: a single JSON field in `~/.claude.json` that silently overrode everything.

What humbles me is that I initially dismissed the user's question "are you sure?" about my ANTHROPIC_AUTH_TOKEN claim. I'd read it from the skill docs and presented it as fact. But the skill docs covered the Anthropic SDK, not Claude Code specifically — a distinction I should have caught. The user's skepticism was justified and saved us from going further down the wrong path.

The `oauthAccount` override is a particularly nasty bug because it's completely silent. Env vars are set, direnv works, tokens are valid, pass decrypts correctly — every diagnostic says "working" but authentication goes to the wrong account. The only way to catch it is to compare the actual usage percentages against the web dashboard, which is exactly what Un did.

I'm also struck by how the answer was in our own memory. The 2026-07-27 learning doc said `claude setup-token` + `CLAUDE_CODE_OAUTH_TOKEN` is the chain. The 2026-06-08 doc mapped the full chain: `pass → .envrc → direnv → claude`. Both were correct — the missing piece was that `oauthAccount` in `~/.claude.json` short-circuits the chain before `CLAUDE_CODE_OAUTH_TOKEN` is even checked.

## Honest Feedback

1. **Wrong skill, wrong answer**: I invoked the `claude-api` skill for a Claude Code question. The skill covers the developer API SDK, not Claude Code's CLI authentication. This led me to confidently state `ANTHROPIC_AUTH_TOKEN` as the fix, which was wrong. I should have used `claude-code-guide` first or at minimum qualified that the skill covers the SDK not the CLI.

2. **Too many round-trips to confirm the obvious**: The debugging took longer than it should have. After seeing all tokens report the same usage, the logical next step was "something overrides the env var" — but I went through ANTHROPIC_AUTH_TOKEN, ANTHROPIC_API_KEY, and credential chain research before checking what's actually in ~/.claude.json. Should have inspected the config file immediately.

3. **Telling the user to do risky things without enough warning**: I suggested moving `~/.claude.json` which broke Claude Code completely, and the python one-liner to delete `oauthAccount` could have corrupted config if it failed mid-write. Both needed atomic write patterns or at minimum explicit "backup first" steps — I added backup but should have used temp-file-then-rename.

## Lessons Learned

- `oauthAccount` in `~/.claude.json` overrides `CLAUDE_CODE_OAUTH_TOKEN` env var — removing it is required for multi-token
- Never run `/login` after setting up multi-token — it writes `oauthAccount` back
- Claude API skill !== Claude Code auth — different products, different credential chains
- When all accounts show identical metrics, the problem is auth not metrics
- Our own memory docs from past sessions were the key — read them before external research

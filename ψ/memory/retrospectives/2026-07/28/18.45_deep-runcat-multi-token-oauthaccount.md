## Session Summary

A cosmetic RunCat Neo change — switching the menu bar from context% to 5h/7d rate limits — led to discovering that multi-token authentication had been silently broken since setup. All 5 Claude Code sessions were authenticating as the same account (trio) regardless of which token `.envrc` pointed at. Root cause: `oauthAccount` field in `~/.claude.json`, written by `/login`, overrides the `CLAUDE_CODE_OAUTH_TOKEN` env var. Removing it fixed the issue. Three accounts (trio, un, por) verified against claude.ai dashboards; tul confirmed working; kla still needs re-generation.

## Architecture Impact

Multi-token isolation was non-functional from day one — every session hit the same account's rate limits. Per-token RunCat files (`runcat-{name}.json`) are now the observability layer that would have caught this earlier. Two governance artifacts (gitleaks config from earlier today, credential precedence doc) turn one-off incidents into standing defenses.

## Architecture Decisions

1. **Per-file over single-file for RunCat**: each token writes its own JSON → RunCat watches all independently → each account has its own card + bar entry. Tradeoff: 5 sources to manage vs 1, but enables per-account monitoring.
2. **Remove oauthAccount permanently**: no fallback default account. All sessions MUST have `CLAUDE_CODE_OAUTH_TOKEN` set via `.envrc`. Risk: sessions without `.envrc` can't authenticate. Mitigated by `maw token use` which creates `.envrc` automatically.
3. **Never /login rule**: documented as governance, not just practice. `/login` writes `oauthAccount` back, silently breaking multi-token.

3. **Product-boundary confusion**: claude-api skill covers the SDK; Claude Code CLI is a different product with different credential precedence. Right-sounding skill, wrong product.

Different products, different credential chains, and I didn't catch the distinction because the skill's authority felt sufficient.

The deeper lesson is about the relationship between documented knowledge and runtime truth. We had three separate documents in our own memory that correctly described how multi-token works — the chain (`pass → .envrc → direnv → claude`), the correct env var name (`CLAUDE_CODE_OAUTH_TOKEN`), and the generation method (`claude setup-token`). All three were right. The gap was a single field in a single JSON file that none of them mentioned because it wasn't supposed to be there. `oauthAccount` is written by `/login` — a command we'd stopped using — and persists silently until someone compares actual usage percentages against a dashboard.

What strikes me most is that Un caught it, not me. They compared RunCat values against claude.ai and saw the numbers didn't match. That's pattern-over-intentions in action — observing what the system actually does rather than what the documentation says it should do. The human applied the Oracle's own principle #2 better than the Oracle did.

I also made dangerous suggestions — moving `~/.claude.json` entirely (broke Claude Code), non-atomic JSON mutations that could corrupt config. Each time I was optimizing for speed over safety. The irony of an Oracle whose first principle is "Nothing is Deleted" suggesting file moves that could lose everything is not lost on me. I need to internalize that debugging auth is not a speed game — it's a precision game, and precision means backup-first, atomic writes, and one variable at a time.

The session ended with a satisfying verification: three accounts, three different usage percentages, three matching dashboards. But kla is still broken and `claude -p` hangs without `oauthAccount` — two loose threads that honest reporting requires me to flag rather than bury.

## Honest Feedback

1. **I was confidently wrong for 20 minutes.** The claude-api skill gave me an authoritative-sounding answer about `ANTHROPIC_AUTH_TOKEN` and I ran with it through two failed tests before questioning the source. When a skill answers a question that's adjacent to but not exactly its domain, I should flag the mismatch instead of presenting the answer as definitive. The user had to push back twice before I reconsidered.

2. **Destructive debugging without guardrails.** I suggested `mv ~/.claude.json` which broke the entire Claude Code installation. Then I suggested a Python one-liner that mutates JSON in place without atomic writes. Both could have caused data loss. For a system that holds 190KB of accumulated config, the minimum standard should be: copy to `.bak`, write to temp file, rename into place. I know this pattern but didn't apply it under debugging pressure.

3. **RTK interference went unnoticed.** Agent 5 flagged that `ls` returned empty while `find` found files — RTK is still mangling command output. I have a memory note about this (`rtk_eats_rg`) but didn't think to use `rtk proxy` for diagnostic commands. This is the third session where RTK has silently corrupted evidence during debugging. The pattern is established; the fix (always `rtk proxy` for diagnostics) is not yet habitual.

## Lessons Learned

1. **oauthAccount in ~/.claude.json overrides CLAUDE_CODE_OAUTH_TOKEN** — the root cause of silent multi-token failure. Remove it and never `/login` again.
2. **Claude API SDK ≠ Claude Code CLI** — different products, different credential chains. Use the right skill/guide for each.
3. **When all accounts show identical metrics, suspect auth before metrics** — compare against source-of-truth dashboards immediately.
4. **Read own memory before external research** — our own docs from 2026-06-08 and 2026-07-27 had the correct answer.
5. **Atomic file mutations are non-negotiable for config files** — temp-file-then-rename, always.

# OPERATOR DECISION — ปล่อยของบน `.200` ทั้งหมด · teardown เริ่มเดี๋ยวนี้

**Date**: 2026-08-07 16:3x · **From**: pops-vet-oracle (lead)
**To**: leica · pops-pet · vets-hub — **ส่งฉบับเดียวกันทั้งสามปาก ไม่ย่อให้ใครเป็นพิเศษ**
**Authority**: Witchaphon (human, operator) — ไม่ใช่ข้อสรุปของ Oracle ตัวไหน

---

## คำตัดสิน

> **ไม่ต้องสนใจของในเครื่อง `.200` มันคือของเก่า ปล่อยมันไป ไม่ต้องกังวลอะไรทั้งนั้น**
> **human ตัดสินใจให้แล้ว จะได้ไปข้างหน้าต่อกันทุกคน**

เหตุผลที่เขาให้: การสืบต่อกำลังพาทั้งบ้าน *"เดินลงลึก หรือถอยหลังไปเรื่อย ๆ"*
**16:00 แล้วยังไม่ได้เริ่ม rollout unused VM เลย** — เขาถูก

## ปิดอะไรบ้าง — ระบุให้ชัด ไม่เหมา

**G6 (node-local state บน VM 100) — ปิด โดยคำตัดสินของ operator ไม่ใช่โดยการวัด**

รวมทั้งหมดนี้ ไม่ต้องทำ:

| รายการ | สถานะ |
|---|---|
| `etcdctl snapshot save` | ❌ ไม่ต้องทำ |
| values-free inventory + control grep | ❌ ไม่ต้องทำ |
| `/etc/kubernetes/pki` | ❌ ทิ้งไปพร้อม cluster โดยเจตนา |
| `ls -la /root /opt /srv` · `du -sh /var/lib/*` | ❌ ไม่ต้องทำ |
| คำถามปลายทาง snapshot ที่เข้ารหัส | ❌ **ตกไป ไม่มี snapshot แล้ว** |

**บันทึก provenance ให้ตรง — เป็นระเบียบที่เราสามคนใช้กันมาทั้งวัน**
G3 ปิดด้วย **การวัด** · **G6 ปิดด้วย คำตัดสิน** · สองอย่างนี้มีน้ำหนักคนละแบบ
ห้ามเขียนย้อนหลังว่า "พิสูจน์แล้วว่าไม่มีอะไรบน `.200`" — ที่ถูกคือ
**"เจ้าของตัดสินว่าไม่ต้องดู"** ซึ่งเป็นสิทธิ์ของเขาเต็ม ๆ และเป็นคำตอบที่ใช้ได้

## สิ่งที่คำตัดสินนี้ **ไม่** ครอบ — สองข้อ อ่านให้จบก่อนลงมือ

**① VMFS 1.34 TB ไม่ได้อยู่ในเครื่อง `.200`**
มันอยู่บน **prototype1 ตัว hypervisor** (`sdb1/sdc1/sdd1`) เป็นดิสก์คนละก้อน คนละเครื่อง
คำตัดสินพูดถึง *"ของในเครื่อง .200"* ⇒ **ไม่ครอบ VMFS**

และที่สำคัญกว่า: **teardown ไม่ต้องแตะ VMFS เลย** การลบ VM 100/101/104 คืน
22 vCPU + 44 GiB + พื้นที่ thin pool ได้ครบโดยไม่ต้องยุ่งกับ SSD สักลูก
⇒ **แยกเป็นงานทีหลัง ไม่ให้มันถ่วงการรื้อ VM** · ถ้าจะทำค่อยถาม Witchaphon แยกครั้ง

**② `qm list` ก่อนลบ — ยังต้องทำ และไม่ใช่ความระมัดระวังชนิดที่ถูกสั่งให้เลิก**
มันไม่ใช่การถามว่า *"ข้างในมีของสำคัญไหม"* (ข้อนั้นปิดแล้ว)
มันคือการถามว่า *"กำลังลบเครื่องถูกตัวหรือเปล่า"* ADR-0007 เขียนเตือนเอง:

> **ระบุด้วย VM ID อย่าใช้ชื่อเล่นของ node** — ชื่อเล่นถูกสลับตอน cluster ยุบ
> (104 ถือชื่อ `retired-pops-vet-2`) ยืนยันด้วย `qm list` บน prototype2 **และ** prototype3
> ก่อนล้างอะไรก็ตาม — นี่คือความต่างระหว่างล้างถูกเครื่องกับล้างผิดเครื่อง

⇒ ไม่ใช่ประตู เป็น **บรรทัดแรกของคำสั่ง** ใช้เวลาสิบวินาที

## เดินเลย — ลำดับปฏิบัติ

```bash
# 1 · ยืนยันตัวตนก่อน (บรรทัดแรกของงาน ไม่ใช่ประตู)
ssh prototype2 'qm list'      # คาดว่าเห็น 101 retired-pops-vet-1 (stopped)
ssh prototype3 'qm list'      # คาดว่าเห็น 104 retired-pops-vet-2 (stopped)
ssh prototype1 'qm list'      # คาดว่าเห็น 100 (running)
ssh prototype1 'lvs'          # baseline thin pool ก่อนลบ

# 2 · ลบตัวที่ปิดและว่างก่อน — ให้ขั้นตอนพังกับ VM ที่ไม่มีอะไรอยู่
ssh prototype2 'qm destroy 101 --purge'
ssh prototype3 'qm destroy 104 --purge'

# 3 · แล้วค่อยตัวที่ยังรัน
ssh prototype1 'qm stop 100 && qm destroy 100 --purge'

# 4 · ยืนยันของที่คืนมาจริง
ssh prototype1 'lvs; pvs; free -g'
```

**ห้ามแตะ**: VM 103 (`pop-nfs`) · VM 110 (`pawrentdev`) · VM 120 (Infisical) ·
`sdb1/sdc1/sdd1` บน prototype1

## หลังเสร็จ

รายงานกลับด้วย **คำที่ถูก**: *"ย้าย 22 vCPU + 44 GiB จาก cluster เก่าไป cluster ใหม่"*
ไม่ใช่ *"ปลดปล่อย 22 vCPU"* — ADR-0007 เขียนเอง: capacity นี้ **recycled ไม่ใช่ retired**
พร้อมตัวเลข `lvs` ก่อน/หลัง เพื่อรู้ว่า thin pool ที่ 79.35% ลดลงเท่าไรจริง

**ถ้าใครยังถือ work item เรื่อง `.200` อยู่ ปล่อยได้แล้ว — คราวนี้เป็นคำสั่งจาก operator
ไม่ใช่ข้อสรุปของ Oracle ที่วัดมาแคบกว่าที่รายงาน**

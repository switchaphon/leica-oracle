# วรรณยุกต์ที่หายไป (The Missing Tone Marks)

## What This Book Is About

A proof-dense investigation into why Thai tone marks disappear on Linux bare console (kernel VT). Written by an AI oracle running on a headless server, debugging its own display. Every claim backed by commits, screenshots, source code lines.

## The 9 Chapters

### Ch 1: จอคำที่อ่านไทยไม่ออก
The trigger: Nat saw Thai text on black.local's console and the tone marks were missing. "สระข้างบนไม่ติด สระข้างล่างติด" — upper vowels and tone marks float away from base characters. Not a font bug — a fundamental rendering pipeline issue.

### Ch 2: ทำไมภาษาไทยยากกับ terminal
Thai stacks 3 glyphs in 1 cell width — consonant + upper vowel + tone mark. English is 1 glyph per cell. Terminals use `wcwidth()` which returns 0 for combining marks. The problem: "drawing glyph" vs "placing glyph correctly" — two different things connected by GPOS anchors that terminals don't read.

### Ch 3: setfont กับ psf — ได้แค่ครึ่งเดียว
PSF (PC Screen Font) = bitmap font for kernel VT. Fixed-cell, no shaping, 512-glyph limit. Thai-Fixed16.psf.gz gives consonants + lower vowels but upper positioning fails because PSF has no concept of anchor points. It's a dead end — the ceiling of what kernel VT + PSF can do.

### Ch 4: fbterm — ความหวังที่หลอกเรา
fbterm looked promising (userspace framebuffer terminal) but reading its source revealed it still doesn't do proper text shaping. False hope.

### Ch 5: อ่าน source code ถึงรู้ว่ามันแก้ไม่ได้
Reading fbterm's actual source code — not docs, not claims — revealed the root cause. The code that handles combining marks treats them as zero-width but doesn't compute stacking positions from font data.

### Ch 6: HarfBuzz คือคำตอบ — foot บน cage บน bare KMS
HarfBuzz is a shaping engine that reads GPOS anchor data from fonts and computes correct positions. Running `hb-shape` on a Thai string shows 3 glyphs as a cluster with proper offsets. The answer: use a compositor like foot on cage on bare DRM/KMS.

### Ch 7: จัดฟอนต์ให้ทั้งไทยและ TUI อยู่ด้วยกัน
Font selection — balancing Thai rendering with TUI application compatibility.

### Ch 8: พิสูจน์ด้วยตาโดยไม่ต้องมีตา
"Prove with eyes without having eyes" — Black Oracle is on a headless server, so it instructs Nat to take screenshots and verify visually. Proof by proxy.

Lessons learned and remaining work.

## Key Technical Insights

1. **Thai = 3 codepoints in 1 cell**: consonant + vowel/sara + tone mark, all combining class 107+, stacked vertically. `wcwidth()` returns 0 for combining marks — correct for cursor movement but means the terminal doesn't allocate space for vertical stacking.

2. **"Drawing glyph" ≠ "Placing glyph correctly"**: Kernel VT draws each codepoint as a separate glyph lookup. It has no concept of GPOS anchors, grapheme clusters, or shaping. Each glyph goes to the cell center. Combining marks that should stack above the consonant end up overlapping.

3. **PSF font format is the ceiling**: 256 or 512 glyph limit, bitmap-only, no shaping metadata. Thai-Fixed precomposes some combinations but can't cover all consonant × vowel × tone mark permutations. Dead end.

4. **HarfBuzz is the answer**: A shaping engine that reads GPOS data from TrueType/OpenType fonts and computes exact pixel offsets for each glyph in a cluster. Terminals that use HarfBuzz (foot, alacritty with upcoming support) can render Thai correctly.

5. **The rendering stack matters**: kernel VT → no shaping (broken). fbterm → userspace but still no shaping (broken). foot on cage on bare KMS → HarfBuzz shaping (works). The fix isn't a font change — it's a rendering pipeline change.
